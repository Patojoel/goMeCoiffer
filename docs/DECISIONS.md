# Décisions — GoMeCoiffer

Décisions d'architecture et décisions métier tranchées. Une décision ne se rediscute pas sans élément nouveau ;
si elle change, on ajoute une nouvelle entrée qui remplace l'ancienne (« remplace D-00x ») au lieu de réécrire
l'historique. Les décisions encore attendues sont listées dans `docs/BACKLOG.md`.

| ID | Date | Décision | Raison | Source |
|---|---|---|---|---|
| D-001 | 2026-11-17 | Persistance **TypeORM** pour les écritures (entités et repositories derrière des ports). Lectures en **SQL pur écrit dans `application/queries`**, exécuté par le port `SqlReader` avec le gabarit `sql` (paramètres liés), jamais par l'ORM. | Choix du user ; garder les lectures optimisables et lisibles, l'ORM limité au cycle de vie des agrégats. | user |
| D-002 | 2026-11-17 | Temps réel par **SSE**, relecture complète à la reconnexion ; **aucun broker** au MVP (outbox + relais en processus). | PRD §12 (SSE ou équivalent, pas de Kafka/RabbitMQ). | PRD |
| D-003 | 2026-11-17 | Le **salon** est le périmètre (tenant) ; le **salon actif** est porté par la session et change le contexte d'autorisation ; rôles système et permissions salon sont deux mondes séparés. | PRD §2-6, BR-12. | PRD |
| D-004 | 2026-11-17 | Authentification par **session serveur** (cookie HttpOnly, stockage PostgreSQL) + CSRF double-submit ; pas de JWT. | Révocation immédiate, changement de salon actif côté serveur, périmètre critique de `CLAUDE.md`. | archi |
| D-005 | 2026-11-17 | Non-chevauchement des réservations garanti **en base** par une contrainte d'exclusion PostgreSQL (`btree_gist`), en plus de la revalidation applicative. | PRD §12 Concurrence, BR-02. | PRD |
| D-006 | 2026-11-17 | Monorepo pnpm : `backend/` (paquet `api`), `frontend/` (paquet `web`), `packages/contracts` (Zod 4 partagés). | Dossiers existants du projet ; contrat partagé API ↔ web (`backend/backendNestjs.md`). | archi |
| D-007 | 2026-11-17 | Montants en **FCFA (XAF) entiers** ; instants en UTC (`timestamptz`), affichage et calcul des créneaux dans le fuseau IANA du salon (`Africa/Douala` par défaut). | PRD §12 Dates, marché Cameroun. | PRD |
| D-008 | 2026-11-17 | Ports locaux : bloc **10400-10409** (API 10400, Vite 10401, PostgreSQL 10402, Mailpit 10403/10404), publiés sur `127.0.0.1`. | Pas de conflit avec VO'SSOU (10370-10389). | archi |
| D-009 | 2026-11-17 | **ESM confirmé** côté API (les paquets NestJS 12 sont publiés en ESM). La CLI TypeORM tourne sur le code compilé (`dist/database/data-source.js`), jamais sur les sources TS. | Socle lot 0. | archi |
| D-010 | 2026-11-17 | **TypeScript 6.0** (pas 7.0) dans tout le monorepo. | `@nestjs/swagger` 12 n'accepte que TS ^5.5 \|\| ^6. À revoir quand il acceptera TS 7. | archi |
| D-011 | 2026-11-17 | Config de l'API par un module maison `AppConfigModule.forRoot(config)` (Zod), pas `@nestjs/config`. | Config typée validée avant la construction du module ; les tests E2E passent leur propre config sans dépendre de `process.env`. | archi |
| D-012 | 2026-11-17 | Entités et migrations déclarées dans des **registres** (`src/database/entities.ts`, `src/database/migrations.ts`), pas par glob. | Les globs de fichiers ne marchent ni sous Vitest ni de façon fiable en ESM sous Windows ; un registre est vérifié par le typecheck. | archi |
| D-013 | 2026-11-17 | Santé exposée par `GET /api/public/health` (ping SQL), sans `@nestjs/terminus`. | Un seul indicateur utile au MVP ; une dépendance de moins. | archi |
| D-014 | 2026-11-17 | React Compiler activé par l'option native `react({ compiler: true })` de `@vitejs/plugin-react` 6 (marquée expérimentale), pas par Babel. | Pas de chaîne Babel dans Vite 8 ; repli documenté dans `docs/frontend.md` si l'option pose problème. | archi |
| D-015 | 2026-11-17 | pnpm 11 : seul `@swc/core` est autorisé à exécuter un script d'installation (`allowBuilds`) ; les exclusions de la politique d'âge des versions sont tenues dans `pnpm-workspace.yaml`. | Surface « supply-chain » minimale. | archi |
| D-017 | 2026-11-17 | **Personnel des salons** : connexion par téléphone + mot de passe (`argon2id`) ; code SMS (OTP) exigé seulement pour les actions sensibles : première connexion / activation d'une invitation, mot de passe oublié, changement de numéro. | Peu de SMS payants, réseau lent toléré au quotidien, sécurité renforcée là où le risque est réel. | user |
| D-018 | 2026-11-17 | **Clients de la marketplace** : compte léger sans mot de passe ; le numéro vérifié par SMS (OTP) est l'identifiant ; une vérification ouvre une session client qui donne accès à « Mes réservations ». Un client et un membre du personnel ayant le même numéro sont **le même utilisateur** (PRD §3 : une identité unique). | Réservation sans application ni mot de passe (PRD F03), historique retrouvable. | user |
| D-019 | 2026-11-18 | **Non-énumération des comptes** : l'écran de demande de code est identique quel que soit l'état du numéro ; si le numéro a déjà un compte avec mot de passe, son titulaire reçoit un SMS d'information sans code. | Personne ne peut tester si un numéro est inscrit ; coût borné par le quota d'envois (UC-001 Q1). | user |
| D-020 | 2026-11-18 | **Mot de passe du personnel** : 10 à 128 caractères, refus des mots de passe courants et de ceux qui contiennent le numéro ; aucune règle de composition imposée ; empreinte argon2id. | Longueur et rareté protègent mieux que la composition, sans frustrer sur téléphone (UC-001 Q2). | user |
| D-021 | 2026-11-18 | **Envoi des codes SMS** : renvoi après 60 s, 5 codes au plus par numéro et par heure, plus une limite par adresse IP ; une tentative échouée chez le fournisseur ne compte pas. | Équilibre coût SMS / réseau lent (UC-001 Q3). | user |
| D-022 | 2026-11-18 | **Consentement** : l'inscription exige l'acceptation des conditions d'utilisation et de la politique de confidentialité ; la date d'acceptation est conservée. | Conformité au cadre camerounais des données personnelles (PRD §12, UC-001 Q5). | user |
| D-023 | 2026-11-18 | **Complète D-021** (revue sécurité de UC-001) : les limites d'envoi s'appliquent **par numéro et par motif** ; en plus de 60 s et 5 par heure, au plus **10 codes par 24 h** et **plus aucun code après 10 codes faux en 24 h**. Les demandes d'un même numéro sont sérialisées par un verrou PostgreSQL. | Sans plafond sur 24 h, deviner un code à 6 chiffres réussissait environ 1 fois sur 1 670 par jour (≈ 20 % par an) ; un quota commun à tous les motifs aurait permis de bloquer la réinitialisation du mot de passe d'un tiers. Seuils ajustables par le user. | revue sécurité |
| D-024 | 2026-11-18 | **Structure d'un module backend** : un fichier par concept, rangé par rôle. Domaine : `aggregates/`, `value-objects/`, `enums/` (objet `as const` + type), `exceptions/` (une erreur par fichier), `events/`, `repositories/write/` (TypeORM, charge et sauve des agrégats), `repositories/read/` (lecture utile à une commande, implémentée en SQL pur dans `application/read-repositories/`), `ports/`, `services/`, `messages/` (textes des SMS). Application : chaque commande a 3 fichiers (`.command.ts`, `.handler.ts`, `.response.ts`). Infrastructure : `persistence/orm-entities/` et `persistence/typeorm-repositories/`. Le `SqlReader` lit dans la transaction en cours quand il y en a une. | Fichiers courts et faciles à trouver ; écriture (ORM) et lecture (SQL pur) séparées jusque dans les repositories ; la réponse d'une commande est décidée par l'application, pas par le contrôleur. Une lecture faite pendant une commande voit ses propres écritures et n'occupe pas une 2e connexion du pool. | user |
| D-025 | 2026-11-18 | **Essais de connexion et appareil reconnu** : les blocages ne visent que les appareils non reconnus. Par numéro (qu'il ait un compte ou non) : 15 min de blocage au 5e échec en 15 min, et blocage tant que 24 h glissantes comptent 20 échecs ; par adresse réseau : blocage tant que l'heure glissante compte 30 échecs. Un appareil où le titulaire s'est connecté avec succès dans les 90 derniers jours est reconnu (cookie, jeton haché en base, propre à chaque compte, conservé à la déconnexion) et n'est jamais bloqué ; à son 5e échec il perd sa reconnaissance. « Mot de passe oublié » (UC-003) lève les blocages. Les essais d'un même numéro sont sérialisés par un verrou PostgreSQL. | Freiner la recherche de mot de passe (≤ 20 essais/jour/numéro) sans qu'un tiers puisse empêcher un propriétaire de se connecter (UC-002 Q1, Q2). | user |
| D-026 | 2026-11-18 | **Durées de session** : personnel 24 h sans activité et 7 jours après la connexion ; utilisateur portant un rôle système 2 h sans activité et 12 h après la connexion. | Pas de mot de passe à retaper chaque matin au salon ; administration de la plateforme mieux protégée (UC-002 Q3, backlog du socle). | user |
| D-027 | 2026-11-18 | **Étape suivante après la connexion** : rôle système → administration ; une seule appartenance active → ce salon s'ouvre ; plusieurs → choix du salon ; aucune → « Créez votre organisation ou demandez une invitation ». | Un clic de moins au quotidien pour le cas le plus courant (UC-002 Q4). | user |
| D-028 | 2026-11-18 | **Connexion, suite** : audit de la connexion réussie, du blocage d'un compte existant et de la déconnexion, sans numéro ni adresse réseau ; historique des essais (avec adresse réseau) purgé après 48 h ; empreinte du mot de passe recalculée à la connexion réussie quand les réglages argon2id augmentent ; sessions simultanées illimitées, pas de « déconnecter mes autres appareils » au MVP. | Collecte minimale des données personnelles ; mots de passe renforcés sans action de l'utilisateur ; téléphone + tablette du salon en même temps (UC-002 Q5-Q7). | user |
| D-029 | 2026-11-18 | **Notification Discord** à chaque mise à jour de `develop`, par GitHub Actions : auteur, titres des commits, identifiants courts et lien vers les différences. URL du webhook dans le secret `DISCORD_WEBHOOK_URL`. | Suivre la préprod depuis Discord ; un workflow filtre la branche (le webhook GitHub natif enverrait toutes les branches). Format confirmé par le user après un essai sans identifiants ni lien. | user |
| D-030 | 2026-11-19 | **Mot de passe oublié, envoi du code** : un défi est créé pour tout numéro et la réponse est identique ; un numéro sans compte ou un compte client léger ne reçoit **aucun SMS** (la demande compte dans les limites D-021/D-023, motif `PASSWORD_RESET`) ; pour un compte du personnel, le SMS part **après la réponse** (une panne n'est pas annoncée et la demande ne compte pas). Texte : « GoMeCoiffer : votre code pour changer de mot de passe est 482913. Il expire dans 5 minutes. Ne le communiquez à personne. » | Ni le temps de réponse ni une panne ne révèlent un compte (D-019) ; aucun SMS payant déclenché vers des inconnus (UC-003 Q1, Q2, Q9). | user |
| D-031 | 2026-11-19 | **Effets d'une réinitialisation** : connexion automatique (session neuve, nouveau jeton, appareil reconnu) ; nouveau mot de passe non comparé à l'ancien ; blocages de connexion **du numéro** levés (15 min et 24 h), pas ceux d'une adresse réseau ; **tous les appareils reconnus révoqués**, sauf celui de la réinitialisation qui redevient reconnu ; **toutes les sessions fermées** par une version des identifiants vérifiée à chaque requête (D-028). | Un téléphone volé ne garde aucun avantage ; la comparaison à l'ancien mot de passe permettrait de le deviner ; une session en cours ne peut pas revivre (UC-003 Q3-Q6). | user |
| D-032 | 2026-11-19 | **Risques acceptés au MVP** (UC-003) : numéros recyclés par les opérateurs (le nouveau titulaire peut réinitialiser le compte de l'ancien), réinitialisation tracée dans l'audit, mesure à décider avant la production ; un tiers peut épuiser les 10 codes/jour d'un numéro et bloquer sa réinitialisation 24 h, la connexion habituelle restant possible (D-023). | Coût d'une parade jugé disproportionné au MVP ; décision à revoir avant la production (UC-003 Q7, Q8 ; backlog C3). | user |
| D-033 | 2026-11-19 | **Remplace un point de D-030** (revue sécurité de UC-003) : une demande de code de réinitialisation **compte toujours** dans les limites (60 s, 5/h, 10/24 h), même si le SMS n'a pas pu partir ; la panne est seulement journalisée (type et code d'erreur, jamais le numéro ni le texte), le défi expire normalement et ses essais ratés restent comptés. | Retirer une demande en panne ne profitait qu'aux vrais comptes (révélait qui est inscrit) et effaçait les essais ratés (force brute illimitée pendant une panne). Coût : une demande perdue sur 5 par heure en cas de panne. | user (revue sécurité) |
| D-034 | 2026-11-19 | **Contrôleurs sans logique** (conçu par `archi-reviewer`) : (R1) un refus qui doit laisser une trace est levé par le handler avec `RefuseAfterCommit` ; le `TransactionalCommandBus` commite puis lève l'erreur métier (plus de branche `REFUSED` ni de `if` dans le contrôleur) ; (R2) un **mapper de requête** `infrastructure/http/mappers/<use-case>.request-mapper.ts` (fonction pure `to<UseCase>(…)`) est le seul code HTTP qui construit une commande ou une query ; (R3) les effets de transport après le commit (session, cookies, jeton CSRF, composition de la réponse) vivent dans un **répondeur** `infrastructure/http/<x>.responder.ts` ; (R4) un corps de route se limite à `execute(to<UseCase>(…))` puis éventuellement `responder.x(…)` : ni `if`, `try`, `new`, `?:`, cast, `req.session` ni cookie. Vérifié par `pnpm arch` (`controller-builds-no-command`) et un grep de revue. | Toute l'orchestration dans le use case ; l'adaptation HTTP isolée et réutilisable (même répondeur pour la connexion et la réinitialisation) ; la couche application ne connaît jamais HTTP. | user |
| D-035 | 2026-11-19 | **Création de l'organisation** : une seule action crée l'organisation, le premier salon et l'appartenance « propriétaire » ; **une seule organisation par utilisateur**, garantie en base (double clic sans effet) ; l'organisation prend le nom commercial du premier salon ; le nom d'un salon n'est unique qu'au sein de son organisation. | Un écran de moins pour un propriétaire non technique ; pas d'organisation vide (UC-004 Q1, Q2, Q13). | user |
| D-036 | 2026-11-19 | **Premier salon** : 6 informations obligatoires (nom commercial, type d'activité, ville, quartier, point de repère, téléphone commercial) ; **ville dans une liste fermée** tenue par GoMeCoiffer, quartier en texte libre ; photo, description et horaires dans des étapes suivantes sauvegardées à part ; téléphone commercial non vérifié par SMS (public après publication) ; adresse publique attribuée à la publication (lot 3) ; salon utilisable tout de suite, **non publié**, sans abonnement (lot 7). | Recherche marketplace fiable par ville ; onboarding court et repris par étapes (UC-004 Q3-Q7, EX-021). | user |

| D-038 | 2026-11-19 | **Qui peut créer une organisation** : un administrateur GoMeCoiffer peut créer la sienne (rôles système et rôles salon restent séparés) ; un collaborateur d'un autre salon aussi ; un compte client léger (sans mot de passe) est refusé et renvoyé vers l'inscription. | D-039 | 2026-11-19 | **Changement de salon actif** : la session est **régénérée à chaque changement** (nouvel identifiant, nouveau jeton CSRF renvoyé ; instant de connexion et version des identifiants conservés) ; seuls les flux temps réel de l'ancienne session sont fermés (les autres appareils ne sont pas touchés) ; le stockage des sessions **refuse de recréer une session remplacée** (requête en vol) ; pas de garde-fou serveur « salon attendu » : un onglet resté sur l'ancien salon doit recharger.
